## 1. 搜尋（subagent_type: Explore；model: sonnet）

```
在《repo 或目錄路徑》裡找出《要找的東西：pattern / 功能位置 / 所有 call site》。
動機：《為什麼要找，找到後要拿來做什麼——這決定你該回報到多細》。
範圍提示：《已知線索：可能的目錄、命名慣例、相關 keyword》。搜尋廣度：《medium｜very thorough》。

驗收條件：
- 覆蓋《明確範圍，如 app/ 與 tests/ 全部 .php》，不得只搜一種命名就停
- 每個結果附 檔案:行號 與一行說明
- 附上你用過的搜尋指令，讓我能複核有沒有漏

回報格式：
- 第一句：找到 N 處（或「沒找到，我搜了 X/Y/Z」）
- 清單：`檔案:行號 — 一行說明`
- 不要貼超過 3 行的程式碼片段
```

## 2. 實作（subagent_type: general-purpose；model: sonnet）

```
實作《功能一句話》。
動機：《為什麼要做、給誰用——遇到規格沒寫到的細節時，照這個動機取捨》。
規格：《輸入/輸出/邊界條件；有 spec 檔就給路徑叫它先讀》。
既有慣例：《該模仿的現有檔案路徑，如「照 app/Services/Xxx.php 的寫法」》。
禁區：《不准動的檔案/行為；例如「不改公開 API」「不加新依賴」》。

驗收條件：
- 《測試指令》全綠；新增分支邏輯要有對應測試
- typecheck/lint 乾淨：《指令》
- 沒有驗收條件外的改動（不順手重構、不加註解、不改格式）

回報格式：
- 第一句：完成/部分完成/失敗＋一句原因
- 改了哪些檔（`檔案:行號` 層級）＋每檔一行「為什麼」
- 測試輸出的最後摘要行（幾 passed 幾 failed），不要貼全文
- 你做了哪些規格沒寫明的決定（讓我能複核）
```

## 3. 重構（subagent_type: general-purpose；model: sonnet；改動 ≥2 檔先問使用者要不要 worktree 隔離）

```
重構《目標一句話：把 X 改成 Y 形狀》。
動機：《現在的痛：為什麼非改不可》。
不變量：**對外行為零改變**。以下必須在重構前後完全一致：《測試清單/API 契約/輸出格式》。
步驟約束：先跑一次《測試指令》記錄基線，再動手；每完成一個檔案就重跑。

驗收條件：
- 重構前後測試結果完全一致（同樣的 passed 數，不允許「修好了順便讓別的測試變綠」）
- diff 裡每一行改動都能對應到重構目標；出現無關改動就是不合格

回報格式：
- 第一句：完成/失敗
- 基線測試結果 vs 完成後測試結果（兩個摘要行並列）
- 改動檔案清單＋每檔一行說明
- 過程中發現但**沒動**的問題（dead code、壞味道）另列一節
```

## 4. 研究（subagent_type: general-purpose；model: sonnet；判斷含糊或高風險時 opus）

```
研究問題：《一句話問題》。
動機：《要用這答案做什麼決定——這決定你該挖多深、哪些細節重要》。
來源優先序：《官方文件 > 原始碼 > issue 討論 > 部落格；或指定必讀來源》。
已知：《我已經知道的，不用重查》。

驗收條件：
- 每個結論附來源（URL 或 檔案:行號），沒有來源的推測要標「推測」
- 覆蓋《必答子問題清單》
- 查不到就明說查不到，不准編造

回報格式：
- 第一句：結論（如果問題是選擇題，直接給建議選項＋一句理由）
- 各子問題：答案＋來源
- 長篇整理落檔到《路徑》，回報只給摘要＋路徑
```

## 5. 審查（subagent_type: general-purpose；model: opus；驗收自己產出時必用 fresh-context、prompt 不可透露作者）

```
審查《檔案/diff/文件 路徑或範圍》。
你是外部審查者，事前不知道作者意圖，只依下列判準審。
判準：《驗收條件清單——具體到可打勾；例如「所有 API 錯誤路徑都有測試」「文件宣稱的指令實際跑得動」》。
攻擊面：《要特別懷疑的地方：邊界條件/並發/幻覺引用/規格漏項》。

驗收條件：
- 每個 finding 附 檔案:行號＋一句缺陷描述＋一個具體的失敗情境（什麼輸入會炸）
- 給不出失敗情境的 finding 不要報（那是意見不是缺陷）
- 找不到問題就明說「判準內未發現」，不准硬湊

回報格式：
- 第一句：通過/不通過＋致命問題數
- findings 按嚴重度排序：`[嚴重度] 檔案:行號 — 缺陷 — 失敗情境`
- 最後一節：判準之外注意到但不確定的事（≤3 條）
```

## 使用備忘

- 模板是底線不是上限：任務有特殊風險就加驗收條件，但三件套不可少。
- 同一批派工能平行就平行（一則訊息裡多個 Agent 呼叫）。
- agent 回報不合驗收 → 走 dispatch.md §5 升降級，不要收下爛回報自己補救。
