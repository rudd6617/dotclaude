## 1. 何時算真的完成

「完成」= 以下四項全過，缺一項就不准說「完成了」，只能說「做到哪、剩什麼」：

1. **驗證跑過**：測試/typecheck/lint 實際跑過且結果貼在回報裡（摘要行即可）。
2. **自己看過效果**：UI 改動要實際打開頁面走過受影響流程（含被你改動「順帶波及」的相鄰功能，例如改日曆格子樣式後要點一下換月）。「typecheck 過了」不等於「畫面對了」。
3. **附驗證入口**：告訴使用者去哪看、怎麼操作、測試資料在不在（沒有就先 seed 或明說沒有）。
4. **查核類任務窮盡清單**：任務是「檢查/盤點 X」時，回報必附「已查項 vs 未查項」清單；中途收工要明說，不准讓「查了一部分」看起來像「查完了」。

- ✓ 正例：「排房改型完成。測試 242 passed。驗證：`:8080/reservations` → 開任一預計CI → 排房 → 打開『允許改型』。測試資料已 seed 三筆。」
- ✗ 反例（實際發生）：回報「改好了」但 vite 跑的是 build 產物，使用者瀏覽器看不到任何變化，來回追問 8 輪才發現驗證環境根本不對。改前端第一步先確認 dev/watch 在跑、走哪個 port。
- ✗ 反例（實際發生）：「檢查完成」後使用者連兩次說「再幫我**完成**檢查一次」——第一輪根本沒查完就停，還宣稱完成。

## 2. 何時停下來問使用者

**該問**（符合任一條就停，列選項讓使用者選，不要自己挑）：
- 業務語義沒有依據：領域詞（口徑、狀態碼、計算規則）在 spec/Wiki/legacy 系統裡都查不到定義。先查再問；查得到就不用問。
- 動作不可逆或對外：刪資料、force push 共用分支、對外發送、改公開 API 契約。
- 需求有 ≥2 種合理解讀，且選錯的返工成本 > 問一次的成本。
- 使用者的訊息是**問句**：他在問你意見，不是叫你動工。回答完停下，等明確的 go/ok/選項編號才動手。

**不該問**（自己決定，事後在回報裡列出你做的決定）：
- 有既有慣例可循的實作細節（命名、檔案位置、錯誤處理寫法——模仿隔壁的現有程式碼）。
- 查得到答案的事實（版本號、API 簽名、legacy 行為——去查，不要拿「請問是不是…」浪費使用者一輪）。

- ✓ 正例：「『團體』的定義 legacy 有兩種行為（A：≥5 房；B：有 group_code），影響報表口徑，選哪個？」
- ✗ 反例（實際發生）：需求模糊處自行拍板業務口徑沒查 legacy 也沒標註，事後被逐條翻案：「你做了什麼決策」。**默默決定 = 最貴的決定。**
- ✗ 反例（反向）：「請問變數要叫 roomTypeId 還是 typeId？」——這種不要問，照隔壁檔案的慣例。

## 3. 方向錯了的訊號（換路，不是重試）

以下訊號出現時，停止當前路線，退回上一個決策點換方法——原樣再試一次是被禁止的：

- **同一個修法試了 2 次都沒過**：第 3 次前必須換：換假設（是不是根本不在這層）、換工具（加 instrumentation 而不是再猜）、或升級模型（見 dispatch.md §5）。
- **使用者第二次講同一句糾正**：代表你上一輪「以為改對了」。這不是再改一次的訊號，是「你的驗證方法有洞」的訊號——先修驗證方法（截圖自證、實際操作一遍），再修代碼。
- **修 A 壞 B 連續出現**：不是繼續打地鼠，是改動面比你理解的大——停下來畫數據流/依賴，或派 agent 掃 call site。
- **越修 diff 越大**：修一個 bug 的 diff 超過原功能的一半，通常代表方案根本不對，考慮還原重來。
- **開始想「特例加個 if 就好」**：連續第 2 個特例 if 出現時，是數據結構錯了（CLAUDE.md 原則 2）。

- ✓ 正例：換月功能修兩次沒好 → 停手，加 console 記錄 state 變化實測，發現是 query key 設計問題，換掉數據結構一次修好。
- ✗ 反例（實際發生）：「側欄是常駐式」講第一次後只改了半套又回報完成，25 分鐘後使用者再講一次同一句話。第二次糾正後仍不自驗，就會有第三次。

## 4. 品質底線怎麼驗（最低標準，不可再降）

| 改動類型 | 底線驗法 |
|---|---|
| 後端邏輯 | 相關測試綠 + 新分支邏輯有新測試。修 bug 先寫會紅的測試再修（CLAUDE.md 原則 9） |
| 前端 UI | 打開瀏覽器實走受影響流程（含相鄰互動：切換、翻頁、重整）；有 demo/設計稿就逐區對照，demo 是 source of truth，不要自行發揮 |
| 文件/設定 | 文件裡宣稱的每個指令實際跑一次；引用的每個路徑 `ls` 一次 |
| 重構 | 前後測試結果逐字相同（同 passed 數）；diff 裡每行都能對應到重構目標 |
| 交接（Memory.md 等） | 逐條對 git log 核實，過期條目當場改掉——過期的交接文件比沒有更糟 |

## 5. 溝通底線（講不白 = 沒做完）

session log 復盤裡**最大宗的重複糾正是「看不懂」**（9 次），比任何代碼錯誤都多。規則：

- 領域縮寫/行話（AR、aggregate root、冪等、hydration…）首次出現必附一句白話定義。寫完掃一遍：每個縮寫都解釋過了嗎？
- 選項題格式固定：**一行結論 → 差異表格 → 建議＋一句理由**。選項給穩定編號（A/B/C），之後不重排——使用者用單字元回覆，編號漂移會直接造成誤解。
- 使用者的糾正即規格：一句現象（「不要閃爍」「都是整數」）= 硬規則，立刻全域套用到同類處，不是只修他指的那一處。

## 6. 何時升級模型

判斷細節在 dispatch.md §5。judgment 層的補充判準：**「這題錯了會不會很貴」比「這題難不難」更重要**——便宜模型處理不可逆操作（migration、資料修復、對外 API 契約）即使它「應該會」也要升級或加驗證，因為失敗成本不對稱。
